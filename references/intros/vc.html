📘 呢頁詳細解說（先睇呢度，再落下面文件）

呢個 Tab 解決兩件事：(1) 揀知識庫（KB）後端、(2) 用 context cache + compaction 慳 AFP。核心心法：

  1. 後端唔係一個 — KB 有 8 種 backend、LTM 有 7 種；揀錯 = 價錢、速度、可用性全中招。
  2. 托管後端（viking / context_search / openviking / mem0 / tos_context）唔使你裝 embedding — 服務端包辦，直接扣方案「向量化」費用，最慳。
  3. RAG 嘅 cost 好多時喺「token」唔喺 vector 儲存 — 慳錢主力係上下文緩存 + 壓縮，唔係攻 vector store。

三個「儲存層」搞清楚（最常混淆）

層 提供乜 貴邊度 揀法重點
知識庫（KB） 靜態文檔 RAG 儲存 + 向量化 + 查詢 新起 → viking / context_search
長期記憶（LTM） 跨對話記住用戶偏好/事件 儲存 + 向量化 生產 → viking / mem0；多實例唔好 local
短期記憶（STM） 對話內 context / session 純 model call 唔使特登揀，Runner 內建

一、揀 KB 後端（快照決策）

你嘅情況 揀
新起、冇咩現有 infra viking（托管，服務端切分+向量化+檢索）
已有 OpenSearch / Redis / Milvus 用返對應 backend（慳遷移，但要自己配 embedding）
要 TOS 預簽名上傳 / 托管 RAG context_search
本地 debug local（進程內存，死咗冇 data）

統一入口：KnowledgeBase(backend=...)，agent 自動有 load_knowledgebase 工具；top_k 預設 10 可臨時覆蓋。

二、揀 LTM 後端

  • local 唔可以進 Multiprocess / 多實例 — AgentKit Runtime 多實例時短期記憶都用佢會「每 instance 各自一本」，session 甩錯機就失憶。生產一定要持久化（Viking / Redis / OpenSearch / mem0）。
  • viking（BytePlus 模式） region 固定 cn-hongkong；viking_mem 已棄用 → 自動轉 viking。
  • mem0 托管，要 pip install mem0 + Mem0Config；AI 負責抽取/儲存/檢索，唔使自己整 embedding。
  • 寫入週期：default 累計 10 條 event 或 60 秒觸發；轉 session_id 時自動將上個 session 寫入 LTM。

三、embedding 成本 — 揀錯後端先會貴

  • 向量類後端（local/opensearch/redis/milvus/tos_vector）要你自己裝 extension + 配 embedding model（MODEL_EMBEDDING_API_BASE / MODEL_EMBEDDING_API_KEY），每次檢索前自己計多一次 embedding token 錢（doubao-embedding-vision 計 AFP）。
  • 托管後端 服務端包辦切分 + 向量化 + 檢索，唔使本地 embedding — 向量費用計入雲資源（第二三條線），慳返「自建向量庫 + embedding 模型」兩項成本。

Sales 一句：「想喺方案度掃走『自建向量庫 + embedding 模型』兩項成本，就揀 VikingDB / Context Search——服務端食晒，你只係買儲存同查詢用量。」

實作：綁 KB + LTM 落 Agent（CLI / YAML / VeADK 三條路）

① AgentKit CLI：建 KB 同 Memory 再綁落 runtime

# 知識庫
agentkit knowledge create --name docs-kb --provider-type viking
agentkit knowledge add docs-kb ./docs ./README.md
agentkit knowledge add docs-kb --url https://example.com/guide.pdf --doc-type pdf

# 長期記憶
agentkit memory create --name user-mem --provider-type VIKINGDB_MEMORY

# 綁落 runtime（唔使重新部署）
agentkit runtime update my-agent \
  --knowledge-id kb-xxxxxxxx \
  --memory-id m-xxxxxxxx \
  --auto-release

# 驗證 agent 識答
agentkit invoke my-agent -m "公司請假流程係點？"

② agentkit.yaml：寫死 KB / Memory 綁定

  # - MODEL_EMBEDDING_API_KEY=sk-xxx

③ VeADK Python：建 KB 載入文件 + LTM + 直接檢索

from veadk.knowledgebase import KnowledgeBase
from veadk.memory.long_term_memory import LongTermMemory

# 知識庫（托管後端：服務端切分+向量化+檢索）
kb = KnowledgeBase(backend="viking", index="support_kb")
kb.add_from_directory("./docs")                  # 掃目錄
kb.add_from_text(["公司標準年假為每年 15 天。"])  # 直接加文字

# 直接檢索驗證
entries = kb.search(query="年假", top_k=3)
for e in entries:
    print(e.content, e.score)

# 長期記憶（托管；BytePlus region 固定 cn-hongkong）
ltm = LongTermMemory(backend="viking", app_name="support_agent")
ltm.save_memory(session_id="s1", scoped_id="user-42", content="用戶偏好週五查帳")

四、上下文緩存 — 慳錢主力（Responses API）

  • VeADK 默認開 session context cache；下一輪將「已緩存」+「新輸入」合併先送 model → 重複 token 明顯減少 → 慳 AFP。
  • 睇命中率：每輪 event usage_metadata 有 cached_content_token_count / prompt_token_count，命中率 ≈ cached/prompt。50–95% 係健康。
  • ⚠️ 設咗 output_schema 就自動關緩存 ——「結構化抽取」vs「慳錢」要權衡。
  • cached_content_token_count 低 → 好可能每輪塞咗大 object（成個 file 落 tool return）。

五、上下文壓縮（Compaction）— 第二個慳錢位

from google.adk.apps.app import App, EventsCompactionConfig
from google.adk.apps.llm_event_summarizer import LlmEventSummarizer

summarizer = LlmEventSummarizer(
    model="doubao-seed-2-0-mini",   # 壓縮用細 model，慳 token
    system_instruction="用精簡粵語總結對話重點，保留用戶事實同已承諾事項。",
)
app = App(agents=[agent], events_compaction_config=EventsCompactionConfig(
    compaction_interval=10, max_events=50, max_tokens=8000, compactor=summarizer,
))

注意：每輪壓 = 額外 model call 反而貴；summary 會冇咗細節（用戶 ID/引用冧巴）。經驗法則：intervak 大啲（10–20）、用 mini 做 summarizer、唔截走 tool 返回嘅關鍵 JSON。

實作：慳錢三件套一次過落（cache + KV + compaction）

# agentkit.yaml：唔開 output_schema 先保持 cache 命中
env:
  - MODEL_AGENT_NAME=seed-2-0-mini-260428
  # OUTPUT_SCHEMA 一設即關 Responses cache —— 有結構化需求先衡量再開
# app.py —— App 層塞 cache-friendly 設定 + compaction
from google.adk.apps.app import App
from google.adk.apps.llm_event_summarizer import LlmEventSummarizer

summarizer = LlmEventSummarizer(
    model="doubao-seed-2-0-mini",
    system_instruction="用精簡粵語總結對話重點，保留用戶事實同已承諾事項。",
)
app = App(
    agents=[agent],
    events_compaction_config=EventsCompactionConfig(
        compaction_interval=10,      # 大啲先慳（太細反而貴）
        max_events=50,
        max_tokens=8000,
        compactor=summarizer,
    ),
)

# 每輪之後讀命中率（cached / prompt）
last_usage = response.events[-1].usage_metadata
hit = last_usage.cached_content_token_count
total = last_usage.prompt_token_count
print(f"cache hit rate: {hit/total:.0%}   # 目標 50–95%")

六、話你知嘅「幣」同因果鏈

prompt 排位靚（不變 prefix）→ 引擎 prefix cache 命中 → platform 唔重算
   → KV-cache 需求降 → GPU VRAM 壓力細 → 成本降

（詳見「AI Infra / GPU」Tab 嘅 cache 三層。）

七、實作檢查清單（照做）

  1. 揀 KB backend（新起→viking/context_search；有 infra→對應）。
  2. 揀 LTM backend（多實例→唔好 local；要 product 級→viking/mem0）。
  3. 向量類後端先要配 embedding env。
  4. 開 Responses cache（唔設 output_schema 先慳）。
  5. 設 compaction config + mini summarizer。
  6. 用 usage_metadata 計命中率、校 threshold。

記住

  • 儲存唔貴，token 先貴：RAG 嘅最大成本係「檢索完全文塞入 context」→ 攻緩存同壓縮。
  • 多實例記憶要求持久化：run_sse 404 十有八九係 session 落咗第個 instance。
