六大主題速覽

先睇框架：Agent 等於「模型＋工具＋記憶＋身份＋可觀測」，喺 AgentKit 入面成套由 AgentKit Studio－Runtime－Gateway－Sandbox 呢四個元件砌出嚟。
本指南分開六大主題，每節附「來源」連結，可以直接連去官方文檔。「更多來源」通常放喺該主題最尾。
主題核心問題一頁總結
1 Studio點樣起一個 agent？一堂式揀「工具沙箱」或「雲上開發」或「本地開發」，喺 Studio 揀 Runtime＋綁定工具，直接測試同發布；亦可以全程用 CLI／SDK。
2 Sandbox工具喺邊度跑、點樣跑？每個「工具沙箱」係一套獨特環境，模板分 AIO／Code ／Skills ／Browser 四類，透過 TOOL_* 環境變數注入 agent 度用。
3 Gateway外部工具／服務點入嚟？統一入口管住 Model API、MCP 服務同 Agent Runtime，支援多協議、身份認證、計量同私有網絡。
4 Identity人同機器點認證？入站（調用方向）用 API Key／OAuth；出站（平台取外部服務）用 AK/SK；平台管理用 IAM 用戶組＋Project 權限。
5 Observability出事點查？三層：基礎監控 Metrics（CPU、延遲…）／應用可觀測 Tracing（Span 樹）／日誌 Logs（TLS），全部可以出嚟對齊端到端。
6 Evaluation點樣確認好用？四件法寶：Dataset（樣本）、Evaluator（評分器）、Experiment（執行）、Regression（回歸防倒退）；分 CLI 版同 Studio 版兩條跑道。

主題 1 — Studio（一站式建造平台）

1.1 Studio 係咩？ ↗

AgentKit Studio 係地火山方舟提供嘅 一站式、圖形化嘅 Agent 建造／測試／發布平台。你唔使寫 code 都可以起 agent：揀 Runtime、綁定工具、喺工具沙箱度直接試，試好就發布。佢係三個建造方式之中「最啱初學者」嗰個。

三個建造方式唔使揀死：Studio（GUI）／雲上開發（CLI）／本地開發（SDK）—— 同一隻 agent 可以用不同方式起，最終都係出一個可部署嘅 Runtime。睇1.2。

1.2 三種建造方式（我應該用邊個？） ↗

方式適合邊啲人點樣做特點
Studio非開發者／想快速驗證無 code：GUI 揀元件、綁工具、測試、發布最易上手；入「工具沙箱」直接同 agent 傾偈
雲上開發 CLI開發者、CI/CDagentkit init / config / build / deploy / launch / invoke / status終端機一條龍；同一套 YAML 走晒全部環境
本地開發 SDK要自訂邏輯／自帶框架（FastAPI、LangChain、Coze…）veadk-python，喺你部機起一個 @app.entrypoint最自由；包裝（wrapper）模式可以「舊 code 即時轉 AgentKit」
注意：Studio 內「工具沙箱」嗰啲係 Debug 用嘅臨時環境（例如 common sandbox），同出產品線嘅 runtime 係兩樣嘢。要正式發布先用得。

1.3 開始之前：前置條件同資源概念 ↗

起 agent 之前，你要有呢啲嘢（冇嘅話可以喺 AgentKit 主控台開）：

  • Model Service（模型服務） —— 一個「模型代理」：入面定義 供應商（火山方舟／OpenAI／Ollama…）、供應商嘅 API Key、用邊啲 Model ID、Proxy API Keys（畀下游客端用）、訪問範圍、重試策略、備用模型（Fallback）。每個帳戶・區域最多 1 個。4.3 會再講。
  • Runtime/環境 —— Agent 執行時所需嘅環境（埋〈工具Sandbox〉）。可以額外關聯：Tools Sandbox、Sessions（RDS）、Memory、IFlytek WS。
  • Observability（可觀測） —— 監控 metric／trace／log（主題 5）。
  • 發布前要過：事前檢查（比如「未綁 Available 嘅 Runtime」做唔到 Evaluation），見5.2。
Model Service 設定細節（源自 Creating_model_service）：填嘅嘢包括 Providers（provider 平台名）、API Key、Models（可多個 model ID，例如 DeepSeek-V3）、Proxy API Key（最多 10 個，供下游客端以 ?apiKey=xxx 方式調用，方便隔離計費）、Access Scope、重試同備用模型。好多公司會開一個「隊友善入口」嘅 Proxy API Key 畀成個 team 共用。

1.5 建立 Agent（去 Studio 撳幾吓） ↗

喺 AgentKit Studio 入面，建立流程大概係：

  1. 揀 Runtime —— 冇嘅話㩒「建立 Runtime」，揀 Volcengine（中國市場）或者 BytePlus（國際市場）。
  2. 綁定工具 —— 揀想畀 agent 用嘅工具集（例如 Common Sandbox、自訂工具…）。
  3. 測試 —— 入「工具沙箱」同 agent 對話試吓（嗰度係唔會真正執行外部工具，只係跑 agent 邏輯）。
  4. 發布（Release） —— 發布成正式 Runtime，之後先可以在外面用 API 調用，同一時間只能發布一個版本；詳細發布流程見1.10。
最佳做法：正式之前，一定行完 Evaluation（主題 6） 或者至少喺工具沙箱試完；另外「環境」同「工具沙箱」都設好之後先去發布，唔好淨係靠一次對話就 push 出街。

1.6 測試同發布（Studio 內） ↗

動作喺 Studio喺 CLI（等價）
測試對話工具沙箱入面直接講嘢agentkit invoke
上線撳「發布」→ 揀流量比例agentkit deploy（50%→100% 漸進）

重要：Studio 發布嗰吓唔代表即刻 100% 出街——首次發布預設係 全量（Full）；之後你可以揀 灰度（Grey Release）：由 10% 開始，逐步加百分比（10/20/…/100）遞到 100% 先至正式完成；喺「Releasing（發布中）」狀態期間唔可以再觸發新發布。睇1.10（發布機制）同6.10。

1.7 Studio 可以做到啲咩？（功能清單） ↗

  • 建立／設定 Agent —— Runtime（有 AIO：All-in-One 整合型模式）、模型、工具、Memory 等。
  • 測試同發布 —— 工具沙箱（Debug）、灰度發布（Canary / Grey Release）、版本管理（V1 自動建立，每次發布一版，可以「回滾到此版本」）。
  • 可觀測內建 —— 日誌、監控、追蹤（追溯查 Request ID）。
  • 安全 —— IAM、API Key、私有網絡。
  • 擴展 —— 可以透過 SPA/插件 或 Coze 整合做更深嘅 agent 工作流。
  • Evaluation（Studio 版） —— 內建一套「評測＋回饋」跑道，見主題 6。

1.8 本地開發工具（CLI＋Python SDK） ↗

開發者通常唔用 GUI，改為用 AgentKit CLI（agentkit）＋veadk-python。一個典型流程（全程喺 Terminal）：

# 1. 安裝
pip install --upgrade veadk-python

# 2. 初始化專案（基本模板）
agentkit init weather_agent --template basic

# 3. 執行程式（本地跑，預設 DEBUG logger）
cd weather_agent
python main.py          # 或 agentkit launch

# 4. 跟 agent 傾偈
agentkit invoke "今日香港天文台話聽日幾多度？"

# 5. 睇狀態／設定
agentkit status
agentkit config         # show 目前 config（可以開 multi-env 測試）
CLI 同 SDK 係同一套嘢：AgentKit 嘅「開源起動套件」＝ AgentKit CLI + Python SDK（veadk-python）。SDK 入面會用到 @app.entrypoint 裝飾器嚟標記入口、ToolClient 自動帶起一啲常用工具客戶端（見2.9）。包裝模式（--from-agent）可以將你部機已有嘅 agent 程式（例如自訂 LangChain／自家框架）直接包成 AgentKit runtime，唔使改 agent 核心邏輯。

1.10 常用 CLI 工作流（量產版） ↗

CLI（agentkit）分兩條路行：步驟式（build→deploy→invoke）同睇狀態（status）。由官方 Common 工作流歸納出嚟嘅四條典型跑道：

  1. 起新 agent（快速）：
    agentkit init weather_agent --template basic → agentkit config（配模型）→ agentkit launch（自動 build+deploy+start）→ agentkit invoke "…" → agentkit status
  2. 漸進發布（灰度）：
    agentkit build → agentkit deploy --traffic-ratio 10 → 加得多先至 agentkit deploy --traffic-ratio 100
  3. 包裝舊 agent（wrapper mode）：
    agentkit init --from-agent ~/my_projects/weather_agent.py —— 部機已有嘅 agent 程式直接變 AgentKit 專案，唔使重寫。
  4. 多環境：
    同一份 project 用 agentkit config 切內測／灰度／正式環境，都係「一套代碼，多個部署」。
發布狀態機：Runtime 一入 Releasing（灰度中）狀態，就唔可以再觸發新發布，要遞到 100% 先定案；每次發布出一版，隨時可以回滾到之前嘅版本（V1 喺建立 Runtime 時自動建立）。

主題 2 — Sandbox（工具沙箱）

2.1 工具沙箱係咩？ ↗

Tools Sandbox（工具沙箱）係 AgentKit 入面 隔離兼安全 嘅「工具執行環境」。每個工具都係一個沙箱實例（sandbox instance），agent 透過 SDK／API 傳嘅 指令 喺沙箱入面執行；平台會幫你管理實例嘅 生命周期（點建立、點重用、點回收、幾時睇日誌）。

執行位置：沙箱喺邊度跑有幾種部署模式——平台雲沙箱／客戶 Worker／本地執行（Provider Cloud / Customer Worker / Local，見1.4 企業部署模式）。要訪問內部系統／敏感數據通常揀 Customer Worker，先做到隔離同審計。
  • Code Sandbox：寫 code、跑 code（Python／Node.js），配 TOS 檔案儲存。
  • Browser Sandbox：真正開一個瀏覽器（自動化網上操作、截圖、爬資料）。
  • Skills Sandbox：用「Skills」執行複雜工序（PDF 解析、AI 搜尋、Excel 操作…）
  • AIO（All-in-One）：一次包晒以上嘅「通用型」，一個 agent 用晒。

2.5 Sessions：短期上下文儲存（AgentKit 層） ↗

Sessions 係 AgentKit 提供嘅 短期上下文 功能：將 agent 每個回合嘅上下文（對話歷史、變數）存喺一個叫 Session 嘅容器度，agent 下次再嚟可以帶返個 SessionID 繼續傾，適合做「多輪客服／流程續航／跨實例接續」。同 Sandbox instance 係兩個獨立機制。

  • 放喺邊：RDS PostgreSQL／MySQL（雲上 RDS 實例；可以喺控制台「匯入」已有 RDS 資源）。
  • 點用：建立 Session → 要用嘅話喺 agent 對答時帶住 SessionID；Session 之間互相隔離，確保用戶之間唔會洩漏上下文。
  • 關聯 Runtime：Session 資源要「關聯」到 Runtime（AgentKit 會將 Session 相關環境變數自動注入 Runtime），之後該 Runtime 上線，流動嘅多輪上下文就自動接上。
同「Sandbox 嘅 session」唔好撈亂：Sandbox 實例都有 session（session_id，見2.6），嗰個係「沙箱執行環境嘅多輪」；Sessions 功能係「Agent 層「對話上下文」嘅儲存」，放 RDS，唔放 Sandbox。

client = ToolClient(

2.8 Snapshot 快照（開長任務） ↗

VM 快照功能：玩緊嘅 Sandbox 實例做 snapshot，之後可以「恢復返實例」繼續。用途係：

  • 長跑任務（training、batch jobs）將狀態存低，唔使由頭起過。
  • 環境用耐咗（patch 過、裝咗嘢）可以一次過「留底」再起過靚環境。
  • 自動備份：實例過期前，如果開咗快照功能，系統會自動做 snapshot（只能恢復一次），之後再過期就清。
Snapshot 唔係萬能：快照唔包含「沙箱外嘅資源」（例如 TOS 有獨立生命周期），而且過期後嘅 snapshot 都會跟住清；長任務建議 定期把成果寫去 TOS，快照只當保險。

主題 3 — Gateway（統一接入網關）

3.1 Gateway 係咩？ ↗

AgentKit Gateway（網關） 係 agent 同外部世界嘅「中央同通訊協定閘」。佢負責：

  • 協定轉譯：將 agent 嘅 function calls／MCP 呼叫轉成外部服務（MCP server／REST API）嘅請求，再轉返嚟。
  • 身份認證：入站同出站兩方向處理 credential（見主題 4）。
  • 計量／計費：數請求（MCP 有 double-count 機制，見3.12）。
  • 網絡：公網／私有網絡（VPC）統一出口。

3.2 Gateway 對象同職責

對象進去（入站）出去（出站）身份
MCP Service / ToolsetMCP 工具俾 agent 用HTTP/MCP/OpenAPI 去外部API Key（inbound）＋AK/SK（出站）
Model ServiceLLM API 口各 model providerProvider API Key ＋Proxy API Key
RuntimeAgent 執行訊（invoke）Sandbox／Memory／Model（Runtime 自己嘅 API Key）

3.3 專屬 Gateway 三大類型（揀錯會冇得玩） ↗

當你要「專屬（Dedicated）Gateway」嘅時候，你開嗰個 gateway 係要揀類型嘅；三類係獨立嘅，而且只可以同對應類型嘅資源關聯：

Gateway 類型可以關聯唔可以
MCP GatewayMCP Service / MCP Toolset（卸載 MCP 工具）Model service、Runtime
Model GatewayModel Service（模型供應商開嘅網關）MCP、Runtime
Agent Runtime GatewayAgent Runtime（已發布嘅 runtime agent）其餘兩類資源
錯誤會點：起咗「MCP Gateway」諗住掛「Model Service」落去，系統會話 resource type mismatch（資源類型唔夾）。所以先決定「我想通嗰樣嘢」，先揀對類型，先至開 gateway。

3.4 兩種模式：專屬 Gateway vs 共用 Gateway ↗

維度專屬 Gateway共用 Gateway

費用按量／包月免費 quota：每戶・區域 2 個 Runtime＋2 個（MCP Service＋Toolset 合計）；超過免費額即照計

功能完整（私有網絡、Plugins 等）核心可用；不支援私有網絡相關進階設定
Shared Mode 重點（Viewing_shared_gateway_information）：共用模式係「按資源類型」嘅一個共用 gateway（MCP 資源共用一個、Runtime 共用一個…），唔係逐個資源細分流量；要出真實產品請用專屬 gateway，並預留私有網絡。

3.5 MCP 協定版本兼容 ↗

AgentKit Gateway 對 MCP（Model Context Protocol）版本有明確定義，而且透過 Streamable HTTP 傳輸；支援呢啲版本（2026-09 為止）：

版本發佈日期特點
2026-07-282026-07-28無狀態：每次請求都帶齊 metadata（MCP-Protocol-Version／Mcp-Method／Mcp-Name header，以及 params._meta）
2025-11-252025-11-25主流／向後兼容
2025-06-182025-06-18主流
2025-03-262025-03-26初版（legacy；較少用）
傳輸做底：HTTP（Streamable HTTP）先係 AgentKit 主要通道；SDK 支援 stdio（本地／包裝用），但接雲上 MCP service 都要經 HTTP。SSE-only server 要先 wrapper 做 Streamable HTTP，見3.17 FAQ。

3.6 MCP 2026-07-28 無狀態機制 ↗

喺新版本之下，agent 同 MCP server 之間唔靠隱含 session，而係「每一吓請求」都有 meta；Gateway 會將呢啲資料帶住轉發：

  • MCP-Protocol-Version／Mcp-Method／Mcp-Name header + params._meta（body 入面）。
  • server/discover：server 可以話俾 client 知支援邊啲能力（tool setting）。
  • 計費週期：無狀態協議版本每 24 小時 開一條週期性「哋」連線；有狀態嘅就每 60 分鐘（見3.12）。

3.7 MRTR（多輪請求流） ↗

MRTR = Multi-Round Task Request，係 AgentKit 為「一輪 agent 對話內，一個 tool 要同外部服務多輪互問」而設：

  • 一個 MCP request 可以有 resultType: "input_required" 之後外部答返 inputRequests / inputResponses；兩邊用同一個 requestState 夾返。
  • 最後一個「最後答案」會用 resultType: "complete" 返去 agent。
典型例子：agent 叫「check order status」，server 開頭答 input_required（要你畀 order id），agent 補 id 再答返 inputResponses，最後 server 回 complete 連 status 資料。呢個機制令「真正需要兩階段嘅 API」都做到對話。

3.8 MCP Toolset：三種模式（配工具畀 agent） ↗

模式點揀工具適合場景
Full Return所有 tool 全數注入 agent工具少（≤ 約 20 個）／都要用
Semantic Retrieval用 embedding 做語義檢索，揀「相關」嘅 tool通用型 agent、工具多；SDK 用 mcp_search_tool／mcp_use_tool
Tag Retrieval用 tool tag 做精準檢索垂直領域 agent（例如指定「finance」嘅 tools 先用）；SDK 用 mcp_list_tools_by_tags
改模式：Toolset 模式係「更新 tool calling 模式」改得嘅（Updating_tool_calling_mode）；工具多過頭（>20）但係用「Full Return」會塞爆 context／令 agent 揀錯，建議轉 Semantic。

3.9 建立 Gateway／MCP Service／MCP Toolset ↗

  1. 起 Gateway（Add MCP Gateway）：揀「MCP Gateway」類型；Private network 開住　可以之後先接 VPC。
  2. 起 MCP Service：入 gateway 內撳「Create MCP Service」；揀「HTTP（Streamable HTTP）」或者「HTTP to MCP（OpenAPI→MCP，見3.11）」。填服務名、網域（domain URL）、入站認證（API Key／OAuth JWT，最多 5 組）＋出站認證。
  3. 起 MCP Toolset：揀「MCP Service」→ 逐個工具「Add」入 toolset；或用「Full/Semantic/Tag」模式自動匹配（3.8）。
  4. Access：MCP Toolset 預設「開啟 Transport」／「Private network」選項照實設定。
建立後唔改得：MCP gateway 嘅使用配置（如 API Key、OAuth、transport）喺建立後唔可以修改；要改就要再起一個。Toolset 亦唔可以加入只開咗 private network 嘅 MCP Service。

3.10 將現有 MCP Server 整合入 Gateway ↗

已經有自建嘅 MCP Server（用 FastMCP 等工具寫好）？可以直接「接入」AgentKit Gateway，唔使改 server 邏輯：

  1. 後端要求：MCP Server 要有 Streamable HTTP endpoint（例如 https://your-mcp-server.internal:8080/mcp/v1）。唔可以用私有 IP 直連 VPC 之間要用網域名稱（見3.14）。
  2. Gateway 加「一面」：Gateway 會統一幫你加上 入站認證（API Key） 同工具發現（tools/list）——我哋（client）只對 Gateway，唔使理後端。
  3. 驗證連線：用 curl 試 tools/list（見下）通常用嚟確定 MCP 通咗。
  4. 用 VeADK 接：MCPToolset 用 StreamableHTTPConnectionParams 或 mcp_router（見3.15）。
# 驗證 MCP service 通唔通（Streamable HTTP）
curl -sS -X POST "https://your-gateway.example.com/mcp/v1" \
  -H "Authorization: Bearer $YOUR_API_KEY" \
  -H "Content-Type: application/json" \
  -H "MCP-Protocol-Version: 2026-07-28" \
  -H "Mcp-Method: tools_list" \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list","params":{},"_meta":{}}'

已有 REST API（OpenAPI/Swagger 檔），想直接變做 MCP 工具？用 HTTP to MCP：

對比MCP ProxyHTTP to MCP

改後端可能要零改動
適合靈活／要自訂邏輯已有穩定 REST API 想快速接入

做法：

  1. 準備 OpenAPI 檔案（Swagger 2.0 或 OpenAPI 3.0；YAML/JSON）。工具名自動由 operationId 攞。
  2. 喺 MCP Service 撳「Create」→ 揀「HTTP to MCP」→ 上傳 OpenAPI 檔案；揀後端類型（veFaaS / VKE / ECS / 固定網域）同填網域。
  3. MCP Toolset 揀模式（工具多嘅話用Semantic Retrieval）。
  4. 之後 tools/call 就會將 MCP 請求「轉譯」做 HTTP method（GET/POST/PUT/DELETE）＋ JSON body 打去你個 API。

          in: path
          required: true
          schema: { type: string }

        "200":
          description: OK

3.12 MCP 請求計數同計費規則 ↗

位置計咩備註
MCP Toolset 層工具被調用嘅次數計一次
MCP Service 層每條 method request都計一次
Toolset＋Service 兩處各計一次即係「雙重計數」
  • 經「專屬 Gateway」轉發嘅所有 MCP Toolset 請求，Gateway 嗰邊再計一次 → 一個 tool call 喺 MCP 分項會見到 2 倍 QPS（toolset 1 次＋service 1 次＋gateway 再 1 次？唔係——官方睇法：計費上 toolset+service 各計，而 gateway 側另計一項）.實際上官方「每條 MCP 請求會被計一次喺 toolset，一次喺 service；Gateway 側再計一次工具呼叫。

3.18 Gateway FAQ ↗

  • 403（RBAC: access denied）：通常係 API Key 無效／稱錯權限；用有效嘅 API Key（有 toolkit 權限嗰把）嚟調用。
  • 唔使 SSE：AgentKit 對 MCP 用 Streamable HTTP（唔支援 SSE-only endpoint）。SSE 版本／stdio-only 嘅 server：想接就要 wrapper 成 Streamable HTTP（例如用 mcp-proxy／fastmcp 轉一轉），先可以做 MCP Gateway 嘅「外連」。
  • STDIO 自動轉：官方嘅 MCP Service 支援 stdio 方式嘅 server 喺建立時會自動轉做 remote MCP（每次呼叫都會帶住 token／連線資訊），唔使自己做 proxy。
  • Toolset 找不到工具：檢查工具有冇加落 toolset、模式係咪 Semantic（可能揀唔到）。
  • 測試：用 curl tools/list（見3.10）快速確認 gateway 通。

主題 4 — Identity（身份與權限）

4.1 Identity 係咩？ ↗

AgentKit 將「身份」分三層，各有唔同嘅 credential：

方向用咩出現喺點樣計／管
入站（apps → agent）API Key（RBAC）MCP Service / Runtime 被調用瞬間API 層籤發；控制「邊個 agent 可以調邊啲資源」
出站（平台 → 外部服務）AK/SK（靜態 credential）Sandbox 攞 TOS／其他雲服務主控台手動填；AK/SK 一次性顯示
平台管理（人 → 控制台）IAM（用戶＋Project）控制台登入、跨團隊分工主帳號開 IAM 用戶／用戶組，授權策略，畀到佢哋管（有限度）agent

4.2 入站認證（API Key＋RBAC） ↗

想「外面個 app」調用你發佈咗嘅 agent（Runtime／MCP Service），要用你手動籤發嘅 API Key。呢把鑰匙帶住 RBAC（role-based access control，角色權限）：

  • 入站時會驗 Authorization，攞到「邊個 service／toolset 可以用」決定放唔放得個 call 入去。
  • RBAC 透過 user_group（用戶組）同 resource 配置做「能唔能夠access」。常用 header：X-Agentkit-Scope 或 Authorization: Bearer <api_key>。
  • 403 RBAC: access denied 就係呢關唔過。原因多數係「API Key 無效／唔屬於該 service／toolset 未 bind 到位」。
安全貼士：API Key 只喺你控制台見到一次；生產環境要用 Secret Manager／注入環境變數，唔好 hardcode 喺 repo。

4.3 出站憑證（AK/SK） ↗

  • Sandbox 想存取雲資源（例如 TOS bucket），要喺「工具沙箱」設定 AK/SK（AccessKey ID＋AccessKey Secret）或者用 IAM Role。
  • TOS SK 通常用 TOS_ACCESS_KEY/TOS_SECRET_KEY 環境變數掛入 sandbox。
  • 備註：迷你只顯示一次，錯過就要重置（re-generate）。

4.4 平台層 IAM（用戶＋Project） ↗

  • IAM User：一個「人」嘅身份，登入控制台。
  • IAM User Group（用戶組）：一堆人一齊得要權限；加人入組＝自動繼承組權限。
  • Project：資源嘅「屬於邊個 project」嘅歸屬劃分；權限可以「只限某個 project」。
  • 授權方式：指派 IAM Policy（例如「AgentKitDeveloperAccess」）畀用戶／組／project 範圍。
IAM 唔係 Agent 內部嘅 ID：Agent 內部身份淨係 API Key／Bearer token；IAM 係「人管雲資源」嗰層，兩者唔好撈埋。

4.5 IAM 系統默認策略

策略能力

AgentKitReadOnlyAccess唯讀（睇資源、日誌）

4.7 授權 IAM 用戶／用戶組（實作步驟） ↗

  1. 入 IAM 建立「用戶」（或用戶組，之後加用戶入組）。
  2. 喺「權限」揀 AgentKit 相關策略：新手團隊建議 AgentKitDeveloperAccess（可建、可設、可測、可發布，但唔可以拆台）。
  3. 可以限定 Project 範圍：只授權某個 project 嘅資源（避免 A 隊郁到 B 隊）。
  4. 檢查依賴權限：AgentKit 操作仲要少量平台服務，例如：
依賴權限用途

4.11 Runtime 生產安全最佳實踐（上線前 Checklist） ↗

官方「上線前檢查清單」重點：

  • Session 隔離：每用戶一個 user_id／session_id request header（見2.7）；唔好跨用戶共用 context。
  • 敏感資料：輸出入內容要做 masking（一次性密碼、信用卡、手機號等）；唔好將 secrets 放落 agent 輸出。
  • 換 credential：API Key／AK/SK 要定期轉；用 Secret 管理。
  • 網絡：Sandbox 內開咩 outbound 都得？唔好——用私有網絡／白名單收窄；唔好俾 Sandbox 直撞你 RDS。
  • Guardrails（安全防護）：開 LLM Shield／Guardrails 過濾 prompt injection、越權指令；權限：LLMShieldFullAccess（見4.7）。
  • 命令執行：Code Sandbox 有 execute_shell_command 等能力——建議唔好全開，或用「執行白名單」。
  • 可觀測＋審計：開日誌同監控（主題 5），發布後睇到異常即刻有痕。
Runtime 限制提醒：每個 runtime 同時運行 最多 20 個 Sandbox instance（官方明訂，唔可調高）；Sandbox instance 每 Template 並發最多 5 個；容器監測（webShell）唔建議喺 production 開。一次請求 body 最多 16MB；每次 Sandbox 執行最長 scope 見2.13。

4.12 Agent Trust Plane：方案定位同總體架構原則

Agent Trust Plane 係一份「企業 Agent 身份與權限治理方案」：喺唔重構現有系統嘅前提下，將 Agent 對生產資源嘅訪問統一收口到可信入口。佢承諾咗一句：低風險操作自動執行、中風險操作二次確認、高風險操作 HITL 審批；Agent 唔直接持有生產密鑰，所有下游憑據由 Broker 喺授權通過之後按次注入。佢解決四個核心問題：

憑據在哪Agent 唔接觸 GitLab Token、雲 AK/SK、DB 密碼、交易密鑰等敏感憑據4.15

總體架構四條原則——同1.4嘅部署模式、3.14嘅私網接入一齊睇先完整：

  1. 控制面／數據面分離：雲賬號、AK/SK、STS 只用嚟發布同管理；用戶與 Agent 調用一律 OIDC/JWT。
  2. Agent 與任務身份分離：後台任務唔冒充用戶；Agent 唔共享平台級 API Key（對比4.2）。
  3. 策略與憑據分離：Policy 決定「允唔允許」；Credential Broker 只喺授權通過後先注入憑據。
  4. 存量系統原生權限保留：GitLab、Argo CD、AWS/EKS、數據庫繼續用返各自嘅 Token／Role／STS／RBAC／OAuth。
例子：CI 入面隻「自動修 MR Agent」——冇 Trust Plane 之前，佢嘅權限＝佢身上嗰把 Project Token 嘅範圍；有咗 Trust Plane，權限＝4.14 五元組策略＋風險判斷＋HITL，同埋邊個 task 觸發、畀咩憑據、做咗啲咩，全部查得到。

4.14 Policy Engine：五元組策略＋示例策略

Policy Engine 建議用五元組出 Effect（Allow／Deny／RequireApproval／RequireStepUp）：

Subject   = user_id / task_id / agent_id / client_id
Action    = read / create_mr / approve / sync / rollback / transfer / write_config
Resource  = repo / branch / namespace / database / wallet / account / document
Context   = env / time / risk_score / amount / data_classification / approval_status
Effect    = allow / deny / require_approval / require_step_up

4.19 AgentKit MA：三張票 × 四道門（身份治理實作）

AgentKit 多 Agent 場景（AgentKit MA）用「三個人、三個範圍、三張票、四道門」將身份治理落到每一次 API 調用。三個人＝角色，三個範圍＝隔離邊界，三張票＝邊個用咩身份，四道門＝每次調用必過嘅檢查鏈：

三張票持有者簽發方做咩作用範圍關鍵動作
Admin 票
（IAM ／ STS ／ SigV4）		平台管理員雲平台 IAM控制面：配置 Workspace、Environment、Policy、RoleBindingOrg 級別，最高權限Create Workspace・BindRole・SetPolicy
End User 票
（User TIP ／ OBO TIP）		終端用戶（經客戶業務後端）AgentKit MA Identity Service（OAuth 流程）數據面：發起會話、調用 MCP 工具、訪問資源Workspace 級別，會話粒度CreateSession・InvokeTool
Worker 票
（Workload TIP）		Worker 執行節點（Agent Runtime）AgentKit MA Identity Service數據面：認領工作項、執行任務、訪問 Environment 資源Environment 級別，任務粒度ClaimWork・ExecuteTask
四道門佢問嘅問題校驗啲咩失敗結果
1. Policy 允許你嘅角色畀唔畀你做呢個動作？RoleBinding 對應嘅 Role 是否包含請求嘅 Action（CreateSession、ClaimWork…）403 Action Denied
2. RoleBinding 覆蓋你喺呢度有角色嗎？Principal 喺目標 Workspace／Environment 是否存在有效 RoleBinding403 No Role
3. 身份有效你係你咩？JWT／TIP 簽名是否合法、有冇過期、Audience 是否匹配401 Unauthorized
4. PEP 關係正確啲對象屬於同一個體系嗎？Session、Worker、Resource 是否都屬於同一 Workspace／Environment，防跨租戶／跨範圍403 Relationship Violation
睇清楚個重點：End User 票有 OBO（On-Behalf-Of）——用戶授權 Agent 代為操作；Worker 票就限死喺自己個 Environment，任務粒度。所以「用戶話要我刪個 production table」呢類請求，會逐道門彈返轉頭：身份過唔到（User 票冇 Admin 權）→ 403；就算身份啱，PEP 關係唔啱都會 403 Relationship Violation。呢啲對應返其他頁嘅 API Key＋RBAC（4.2）同 Session 隔離（4.11）。

6.1 四件法寶（Dataset・Evaluator・Experiment・Regression） ↗

6.3 Coverage（覆蓋率）：你「測得夠唔夠」？

「覆蓋率」喺傳統編程同 LLM 都係「被檢驗／被包含嘅比例」，但量度對象完全唔同：一個數代碼行數，一個數語意同場景。

① 傳統：代碼覆蓋率（Code Coverage）——測試執行期間跑咗幾多可執行代碼，主要維度：

維度計法點解重要
行／語句覆蓋跑過行數 ÷ 總可執行行數有冇成段邏輯永遠冇跑過
分支覆蓋跑過分支 ÷ 總分支（if/else、switch、loop 嘅 True/False）有冇成個走向冇測
函數／路徑覆蓋被叫函數、行過路徑比例組合性死角
 
Line Coverage = Executed Lines ÷ Total Executable Lines × 100%

# discount.py
def calculate_discount(price: float, is_vip: bool) -> float:
    if is_vip:                  # 分支點：True / False
        discounted = price * 0.8
        return discounted
    return price                # 呢行未跑過

# test_discount.py —— 淨係測 VIP
def test_vip_discount():
    assert calculate_discount(100.0, True) == 80.0

② LLM 版：覆蓋率拆成 4 個維度——LLM 輸出冇「跑邊行」可言，改為量呢四樣：

維度量咩計法例子

  1. 話到首都係巴黎   2. 提到巴黎喺法國   3. 講明「首都」身份

③ 兩者其實會夾埋用：而家工程師會用 LLM 幫手generate unit test快速拉高代碼覆蓋率；但純 LLM 生成好易「跑咗碼但唔斷言」，所以要加變異測試驗證啲測試真係捉到錯。

放喺 AgentKit 點用：覆蓋率唔係內建一粒 score，要你自己喺 dataset 度量。開 dataset 前用呢 4 個維度補場景（見 6.7）：RAG agent 記住「知識點覆蓋」、QA agent 記住「Key Point 覆蓋」、Agent 記住「tool 調用覆蓋」＋「對抗覆蓋」（6.4）。

6.4 對抗集（Adversarial Dataset）：專登「恰」你隻 agent

類型目標例子點樣驗

6.8 Evaluator（評分器）：rubric prompt ＋ judge model ↗

Evaluator ＝ 一段 rubric prompt ＋ 一個 judge model：收 input 欄位、出一粒分（可附理由）。由內建模板 clone 通常好過由零寫：

# 1) 睇有咩內建模板（relevance 等）同個模板入面寫咩
agentkit eval evaluator template list
agentkit eval evaluator template show relevance
# 2) 由模板開，換成自己嘅 judge model
agentkit eval evaluator create \
  --name relevance \
  --from-template relevance \
  --model "Doubao 2.0 Pro"        # TEA；Coze 用 Ark endpoint ID（ep-xxxxxxxx）
# 3) TEA：run 之前一定要提交版本
agentkit eval evaluator version submit 0.0.1 --evaluator relevance
# 4) 睇返設定
agentkit eval evaluator show relevance

自訂 rubric：{{欄位名}} 就係 evaluator 嘅 input schema，run 時自動映射（見「佢哋評咩」）：

// rubric.txt（自訂評分規則）
Question: {{input}}
Reference answer: {{reference_output}}
Actual answer: {{output}}
Check whether the actual answer correctly answers the question and matches the
reference. Score 1 for a correct and complete answer, otherwise 0, and briefly
explain the score.

# 用自訂 rubric 開（--input-schemas 對應模板佔位符欄位）
agentkit eval evaluator create \
  --name custom-score \
  --prompt-file ./rubric.txt \
  --input-schemas input,output,reference_output \
  --model 2                        # TEA：model id；Coze：Ark endpoint id
實務貼士：一次 run 可以掛多個 --evaluator 做加權總分（例如 relevance＋completeness）；judge model 用強啲嘅 Ark endpoint，弱 model 嘅分數會好「嘈」；改完 draft 要重新 version submit 先算數，已提交嘅版本唔會自己更新。

6.10 Studio 自動回灌（Auto Backflow） ↗

  • Studio 內有「自動回灌」：將上線後「用戶同 agent 真對話」抽返入評測集，做回饋閉環。

埋入 CI（例如 GitHub Actions / 每週 cron）——重點係「攞到 experimentId 唔算數，poll 到終態先判斷」：

#!/usr/bin/env bash
# eval-regression.sh —— 失敗就唔准入主線 / 唔准上線
set -euo pipefail
EXP=$(agentkit eval run --dataset qa-set --dataset-version 0.0.1 \
  --evaluator relevance --evaluator-version 0.0.1 \
  --target qa-agent --json | jq -r .experimentId)
for i in $(seq 1 30); do
  STATE=$(agentkit eval experiment show "$EXP" --json | jq -r .status)
  [ "$STATE" = "Success" ] && break
  [ "$STATE" = "Failed" ] && { echo "eval failed: $EXP"; exit 1; }
  sleep 10
done
SCORE=$(agentkit eval experiment show "$EXP" --json | jq -r '.scores.overall')
echo "experiment=$EXP overall=$SCORE"
jq -n --arg s "$SCORE" '($s | tonumber) >= 0.9'   # 門檻：overall ≥ 0.9，false 即 exit 1
結論：dataset 係「考卷」，target 係「考生」，evaluator 係「改卷員」，experiment 係「一次考試」；要比較就要固定 dataset＋evaluator 版本（即 TEA 嘅價值）。分數跌就帶 trace_id 翻去5.13嗰套排查。
